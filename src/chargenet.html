ChargeNet

A small Azure platform for an electric truck charging network, built the way I'd want to find one on my first day in a new team: governed, observable, and changed only through pull requests.

Live status page ↗ Source and architecture ↗

The problem

A charging network is mostly infrastructure nobody sees. Stations along the motorway report their status every few minutes; somebody needs to know within minutes when one breaks or goes quiet, and the platform behind it has to be secure, affordable and safe to change.

I wanted to show I can build that end to end on Azure, with the habits of a team that runs production: no portal clicks, no shared passwords, and every decision written down.

What I built

  • Landing zone. Azure Policy denies resources outside the approved region, untagged resource groups and public IP addresses. A budget alerts at 50, 80 and 100%.
  • Hub-spoke network with a spoke per environment, an NSG per subnet, and a gateway subnet ready for a site-to-site VPN.
  • Environment vending. The platform layer hands each environment its resource group, network and identities; the environment itself is one reusable Terraform module.
  • Telemetry pipeline. Simulated stations publish over MQTT; a processor moves messages into Log Analytics and only advances its checkpoint after a successful write, so a failure re-reads instead of losing data.
  • Observability. Per-station alerts for faulted and silent stations; the silent alert also fires if the pipeline itself stops. A workbook shows status, power and energy per site, fault history and pipeline delay.

Decisions I'd defend in a review

No secrets in pipelines

GitHub Actions signs in with OIDC federation and workloads use managed identities. The two keys that remain are where Azure offers nothing else, and they're documented as such.

A deploy identity that can't escalate

The platform pipeline may assign roles, but an Azure ABAC condition blocks it from granting Owner, User Access Administrator or RBAC Administrator, to itself or anyone.

Public exposure as a recorded exception

The status API is public by decision, not by accident: read-only identity, cached queries, one replica. The ADR also notes what the "no public IP" policy doesn't catch.

One fleet, one ingestion point

Every environment reads the same stream through its own consumer group and read-only key, which keeps IoT Hub on the free tier and mirrors how a real fleet works.

How changes ship

Every change is a pull request. The pipeline builds container images tagged by a hash of their source, plans each Terraform layer and posts the plans as PR comments. Merging applies exactly those plans, platform first. main is protected, even for admins, and a nightly run fails if anything was changed outside Terraform.

What went wrong, and what I learned

  • The free tier's hidden limits. The first IoT Hub deploy failed: the Free tier allows two partitions and Terraform asked for four. Later, a second Container Apps environment failed on a one-per-region trial quota. Both now live in code comments and an ADR, not in my memory.
  • Defaults that drift. Azure silently added a workload profile to new container environments; undeclared, Terraform would have tried to remove it every night and the drift check would never have been green. This is exactly why every plan gets read before it's merged.
  • Least privilege is a design input. Narrowing the dev pipeline to its own resource group meant the platform had to own resource provider registration and role assignments. That shaped the whole layering, for the better.
